## Approved behavior

The user approved explicit `/send` and `/discard` for albums on 2026-10-16. One open
durable album per user fixes the first file's conversation. Files/captions follow source
message order; captions are joined with one newline and are never interpreted as commands.
An album survives restart, expires before acceptance after TTL from its first file, and
cannot reopen after send/discard/expiry. Single supported files submit immediately.

The transport downloads bounded streams into generated private files; the application
rechecks bytes before submission. Runtime fake uploads read the same bytes through
`AttachmentStore`, with SHA-256 receipts asserted in tests. There is no parallel provider
send path. `0005_attachment_batches.sql` atomically moves a draft into the existing
R2 acceptance frame and binds all source updates to that one Request before dispatch.

## Independent review correction

Review of published head `c7f78a2836da76ccddf402800e92a78dcb6d8d9e` returned
**CHANGES_REQUIRED**, with one MEDIUM finding: TTL cleanup could close an existing album
while its next file was downloading; appending to that closed draft raised `DatabaseError`
and stopped polling. This was independently reproduced before the fix. The original head's
author suite passed 366 tests / 2259 assertions; the reviewer inspected source and did not
run Bun tests.

After download, the collector now synchronously expires/rechecks the existing draft before
append. A closed draft produces handled `ATTACHMENT_REJECTED`, releases its preparation
lease and removes the newly downloaded file. Genuine persistence errors still propagate.
The gated-download regression runs the actual Telegram polling loop, expires the draft
while download is paused, then verifies rejection without a Request/provider submission,
dedup evidence, file cleanup, offset advancement and completion of the next text request.
The verification results above include this correction. The final exact-head review verdict
is recorded in the PR description without altering the reviewed commit.

## Upstream contracts inspected

Official Telegram Bot API documentation was inspected on 2026-10-16:

- [Message](https://core.telegram.org/bots/api#message): `media_group_id` identifies a
  group within a chat; there is no count/last-message completion signal.
- [getFile](https://core.telegram.org/bots/api#getfile) and
  [File](https://core.telegram.org/bots/api#file): hosted downloads up to 20 MB, optional
  file size/path and token-bearing download URL; original name/MIME must come from the
  incoming message. R5 conservatively caps hosted downloads at 20,000,000 bytes.
- [Document](https://core.telegram.org/bots/api#document) and
  [PhotoSize](https://core.telegram.org/bots/api#photosize): optional size/name/MIME for
  documents; dimensions and file ID for a photo variant.
- [Sending files](https://core.telegram.org/bots/api#sending-files): one file can have
  different valid file IDs even for one bot; R5 does not assume the returned ID string
  must equal the originally requested one.

## Limits and remaining work

- R6 real browser/provider upload is not implemented or live-tested. Default real start
  still reports the missing adapter. Fake development mode is explicitly labelled.
- ZIP has no confirmed provider capability contract and remains rejected.
- Photo messages accept validated JPEG; other supported images can be sent as documents.
- Type validation uses UTF-8/no-NUL and signatures, not complete file-format parsing.
- Draft expiry and failed physical cleanup use bounded TTL sweep; accepted non-terminal
  or unclassified surviving references have no TTL. SQLite row deletion is not secure
  erasure of WAL/free pages/backups. One runtime owns the MVP database/profile.

  publication of confirmed review fixes on 2026-10-16. No merge is authorized.
