## Changes and intentional behavior

`src/ports/ChatProvider.ts` owns capabilities, normalized health, conversation references,
send/submission, final outcomes, cancellation and read-only request inspection. Schemas
reject malformed evidence and extra upstream fields. Evidence must correlate to the
exact client request and canonical conversation, plus a saved provider request ID if
available. An adapter cannot infer correlation from an unrelated latest message.

`FakeChatProvider` uses manual barriers, synthetic remote state and explicit scenarios:
success, slow generation/partial text, proven pre-submit failure, exception before send,
ambiguous send, failure after confirmed submission, confirmed generation failure, timeout
with/without stopped evidence, cancellation success, completion race, unavailability and
authentication required. The fake does not read files, use network or sleep.

`RequestService` uses the existing durable acceptance/queue/repository path. It records
submission only from a validated receipt, then awaits final evidence and persists terminal
state/retention before delivering the result callback. A raw exception is not proof of
pre-submit failure. Failed delivery is separately reported and cannot resubmit or change
provider-completed state. Application diagnostics retain IDs/codes, not raw exceptions or
prompt/response content.

The queue derives concurrency from provider capabilities and reserves a slot per distinct
unresolved canonical key, including UNKNOWN. This prevents a capability=1 provider from
starting another remote conversation while an earlier generation may still exist. Two
aliases count once. Bare R2 executor queues retain their original explicit-limit behavior;
the R3 service enables the reservation option. Existing admission/dedup/FIFO/claim/shutdown
and retention guarantees remain covered by the original tests.

Stop requires an active confirmed submission and cancellation capability. It persists
cancel_requested, sends at most one cancellation, and joins cancellation and completion
before releasing queue ownership. Confirmed completion wins their race. Acknowledgement
alone cannot mark CANCELLED; later queued requests remain durable. An observer deadline
aborts only the read-only wait, and becomes UNKNOWN unless remote termination is proven.
TIMEOUT is reserved for evidence that the generation ended. A local Bun 1.4.0 probe confirmed
that 2147483648ms becomes 1ms; both configuration and service composition now reject deadlines
above 2147483647ms. The two overflow regressions failed before this validation and pass now.

Startup inspects interrupted work before opening admission/dispatch. Correlated terminal
evidence settles it without another send. Proven not-submitted uploading/sending becomes
failed without retry. Other interrupted work becomes UNKNOWN, including still-running
observations. Existing UNKNOWN and incomplete created/queued evidence remain blocked.
`uploading -> unknown` is the only added domain transition, avoiding artificial send
evidence when classifying interrupted uploads. The existing schema already permits it.
Recovered submittedAt records local evidence observation, not an asserted upstream time.

## Files and limits

- Added ChatProvider port, FakeChatProvider, RequestService and the tests/fixture above.
- Updated Request domain edge, RequestQueue capacity accounting, generation timeout
  validation, domain/config tests, README, ARCHITECTURE and this evidence report.
- `start` is still the one-shot R0 bootstrap; service composition is exercised in tests.
  No R4 Telegram commands, R5 downloads, R6 browser integration or full R7 hardening.
- One scheduler/service owns the MVP database/profile. Capabilities are immutable per
  service lifetime. The future real provider must prove correlation, terminal evidence,
  cancellation and abort cleanup obligations with opt-in integration tests.
- No automatic retries, manual UNKNOWN resolution, interrupted observation resumption
  or durable delivery retry. Delivery failure diagnostics are in-memory; ambiguous keys
  deliberately remain blocked, potentially exhausting provider capacity.
- The application deadline bounds observation through the port's AbortSignal contract.
  Send/cancel cleanup cannot be detached just to free a slot; an adapter that violates
  that contract needs correction, not an unsafe local retry/unlock.
- No live-provider, Linux/Windows or complete MVP acceptance claim. Independent review
  must name the exact published R3 head; the old R2 APPROVE is not an R3 verdict.
