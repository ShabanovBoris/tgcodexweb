## Implementation and preserved invariants

`SqliteRequestQueueRepository` composes the existing request/conversation/update adapters
on one SQLite connection. A single BEGIN IMMEDIATE checks marker/capacity and commits
request, attachments, input, durable retention ownership, update marker and queued state. Duplicate input retains the original
request and payload. Capacity rejection writes nothing and permits later redelivery.
This is the durable acceptance service; no generic transaction abstraction was introduced.

Forward `0003_request_inputs.sql` adds one table. Its AUTOINCREMENT sequence records
committed acceptance order, including identical timestamps and nonlexical request IDs.
Payload contains text and ordered attachment IDs; attachment values have one source in
the existing table. No R1 table rebuild, trigger or migration-language expansion was needed.
Forward 0004 adds request-ID-only durable retention ownership independently of payload.
Terminal transition and R2 input/attachment deletion are one existing request-repository
transaction; failure during cleanup rolls back lifecycle and both input stores together.
This is logical SQLite deletion, not forensic erasure of WAL, freed pages or backups.

`RequestQueue` owns admission and dispatch for one runtime, using the exact opaque
provider conversation ID in the single MVP profile. It persists claim/start before the
executor's first suspension, holds the key for the full async callback, and waits for
durable settlement before selecting later work. Independent keys may execute concurrently;
explicit global concurrency 1 supports a lower execution capability. Shutdown stops
admission/dispatch, awaits active effects and preserves queued input.

Reconstruction checks queued lifecycle, durable acceptance ownership, input, ordered attachment set and originating
marker in one read transaction. Incomplete input is surfaced as `input_unavailable`.
Uploading/sending/running/cancel-requested/UNKNOWN are `reconciliation_required`, never
replayed or rewritten. Their keys block queued successors while other keys can proceed.
Executor rejection is not classified as pre-submit failure; no retry is added. Provider
evidence provenance and resolution of blocked work remain R3/R7 responsibilities.

Preserved: I2/I3 dependency boundaries, I4 serialization, I5 one request per update,
I6 non-replay, I7 no browser-auth inputs/logging, I8 local-only archive, I10 durable ID
before mutation. Owner-scoped rename/archive, released aliases, immutable provider identity,
old request links, FK/CHECK constraints and the published migration prefix are unchanged.
Intentional behavior added: accepted input/retention, durable FIFO/capacity/shutdown and
safe queue reconstruction. No class/function was deleted; the payload-existence ownership
check was replaced by durable acceptance ownership, with its deletion reason recorded.
Obsolete R1-only documentation claims and schema-count expectations were updated. Legacy migration fixtures seed old
lifecycle rows via the existing pure reducer/SQL, while current-schema state tests still
exercise the actual request adapter.
