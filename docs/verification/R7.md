# R7, first slice — Telegram polling reconnect

Date: 2026-10-19 (Europe/Moscow). Base: `c32da2caadb04a19aff71f9008eb6e4a0371fad7`
(main after PR #8). This report covers polling recovery only, not completion of R7/R6/MVP.

## Behavior and boundaries

Only the read of `getUpdates` is retried. The same sequential poller keeps the last handled
offset, the application instance, SQLite connection and active provider work. Known network
codes, the adapter's own polling timeout, HTTP 5xx and an explicit HTTP 429 / `ok=false` /
error-code 429 with valid nonnegative integer `parameters.retry_after` can supply a safe
numeric hint. Original exceptions, URLs and server descriptions are not attached to it.
Unknown network codes and TLS failures remain fatal. A malformed successful payload does
not authorize a retry. HTTP 401 and 409 remain fatal even if their bodies cannot be read;
an unreadable 429 cannot bypass its unknown flood-control delay.

There are at most five consecutive retries, with base waits of 1/2/4/8/16 seconds. Each
wait is the larger of the base and the server minimum, capped by a 60-second policy limit.
A required wait over that limit is rejected without polling early. Missing/invalid 429
delays are fatal, not replaced with a guess. A successful poll, including an empty list,
resets the budget. Transport readiness is false during startup and throughout reconnection;
it becomes true only after a successful poll. AbortSignal interrupts both active polling
and timer waits.

Token validation/initialization, update handling, `sendMessage`, provider submission and
UNKNOWN recovery do not gain retries. The existing explicit HTML-parser rejection fallback
is unchanged. Fatal polling errors still shut down and join active effects once. No new
dependency, configuration, migration, browser adapter change or live request is involved.

## Independent review corrections

Source-only review returned CHANGES_REQUIRED for `88dbdf81c57267a5be621ff4f21dce33473237aa`:
an already-known 5xx lost its retry hint if body reading threw a plain TypeError, and
initial readiness became true before the first successful poll. Both findings were
reproduced offline before the fixes (24 passing / 4 failing focused cases).

The 5xx read path now keeps the known HTTP classification regardless of the body-read
exception; caller cancellation still wins in the outer boundary. No retry hint is added
to sendMessage or unreadable 4xx responses. Removing the premature running transition
keeps startup non-ready until the existing successful-poll transition, including empty
polls. Gated first-poll regressions exercise empty and nonempty responses; API regressions
exercise 500/503/599 with uncoded TypeError/Error, fixed safe errors and caller abort.

## Limits and remaining work

All added tests use injected API/fetch boundaries, FakeChatProvider, temporary SQLite and
temporary directories. No real Telegram/ChatGPT requests, operator profile or live runtime
restart were performed. A local socket-error characterization probe could not bind a
loopback listener in the restricted environment; it supplies no runtime network evidence.
Network error classification is exercised with synthetic errors and an explicit allowlist.
The normal opt-in Chromium cases are not required for this transport-only change; their
R6/PR #8 evidence and recorded initial 404-test timeout are not replaced by this report.

Initial `getMe` recovery, durable delivery retry, UNKNOWN operator UX, doctor and broader
provider recovery remain later R7 work. Full acceptance and live R6 gaps remain open.
The subsequent [operator recovery slice](R7-unknown-recovery.md) covers explicit offline
release of a completed UNKNOWN; the polling-only head above does not contain that change.
The later [operational slice](R7-operations.md) adds doctor/status/UNKNOWN UX, durable
delivery and read-only provider/initial-identity recovery; the earlier limits above refer
to the polling-only revision.
The published head/base and independent review verdict belong in the separate PR; author
test execution is not an independent reviewer's runtime evidence. Merge requires the
user's separate instruction.

## Primary contracts

- [Telegram getUpdates](https://core.telegram.org/bots/api#getupdates): offset acknowledgement and webhook exclusion.
- [Telegram ResponseParameters](https://core.telegram.org/bots/api#responseparameters): `retry_after` is seconds to wait before repeating a request.
- [Bun fetch](https://bun.com/docs/runtime/networking/fetch): timeout/cancellation signals and socket error codes; the allowlist is deliberately narrower than all fetch exceptions.
