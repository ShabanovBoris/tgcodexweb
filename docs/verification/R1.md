## Mandatory migration prerequisites

Before authoring `0001_domain.sql`, the revised runner passed 52 migration tests on
Bun 1.4.0 / SQLite 3.51.0. That included both fresh and initialized COMMIT rejection.
The final migration suite contains 57 tests, adding whole-pending-set COMMIT preflight
and applied-ledger version/name/checksum tampering checks.

The original runner was separately probed in a disposable in-memory database:
`CREATE TABLE x(id); COMMIT;` inside Bun's transaction wrapper left `x` committed even
though the outer transaction failed. Therefore the wrapper alone was insufficient.

The pinned public driver had no `setAuthorizer` API. Its typed `handle` is an internal
index, not a C pointer; no unstable native ABI or custom SQLite library was introduced.
EXPLAIN was rejected as a guard: [SQLite documents](https://www.sqlite.org/lang_explain.html)
that some pragmas act at preparation time even with EXPLAIN.

The chosen guard is a tested lexical preflight of every migration before any SQL:

- Versions start at `0001` and are contiguous; gaps and duplicates fail before SQL.
- Applied files remain an immutable prefix, checked by version, name and SHA-256.
- Statement starts are limited to ordinary DDL/DML. The scanner recognizes SQLite
  [comments](https://www.sqlite.org/lang_comment.html), strings and
  [quoted identifiers](https://www.sqlite.org/lang_keywords.html), including doubled quotes.
- Transaction control, VACUUM, all PRAGMA statements, ATTACH/DETACH and trigger bodies
  are rejected; NUL and unterminated quotes/comments are rejected too.
- Remaining SQL/schema/data/ledger changes run in one BEGIN IMMEDIATE transaction.

This deliberately restricted SQL language is not a sandbox for untrusted SQL authors.
Trigger support requires a separately verified mechanism before it can be enabled.
COMMIT tests compare schema, data, ledger and connection settings after rejection on
fresh and initialized databases. Ordinary SQL failure tests prove transactional rollback
across multiple pending files. Quoted control words and semicolons remain valid data.

The state machine permits `sending -> failed` only with `SEND_FAILED_PRE_SUBMIT` and
forbids that classification after confirmed submission. `unknown` is a settled local
outcome, never success, with no transition back to submission. Cancellation can settle
as cancelled/completed/unknown. The caller must supply actual evidence; R1 has no provider
and does not prove evidence provenance or perform startup reconciliation.

Conversation removal archives only the local mapping, clears selection atomically and
preserves request references. Alias uniqueness includes archived mappings. Active selection
has an ownership composite FK and the adapter rejects archived selections. Provider IDs
are immutable through these repository operations; URLs are not parsed into identity.
Users are metadata for ownership, not an implemented allowlist enforcement service.

Request originating update IDs are unique. Processed-update markers are keyed by update,
and may reference the same request from several updates. The initially overrestrictive
composite update/request FK was removed during authoring: I5 prohibits a second request
per update, not additional markers per request. Its removal reason is recorded in SQL.
No applied production migration was edited; R0 had no production SQL files.

Storage has exactly seven operational tables: `schema_migrations`, `users`,
`conversations`, `active_conversations`, `requests`, `processed_updates`, `attachments`.
Foreign-key checks return no violations and integrity check returns `ok`. There are no
browser-auth, prompt/response or conversation-history columns. Optional free-form
redacted failure details are deferred until a trusted error mapper exists; R1 accepts
only normalized failure codes. Attachment filenames are metadata; optional local storage
references are generated keys, and no files are downloaded or opened by these adapters.
